---
name: cc-bro
description: Read the project roster, choose a permitted CLI, model and effort, then delegate to named persistent workers, steer, review and accept tickets.
---

Stay in the current project. Use the installed launcher {{launcher}} for every command. Quote names, prompts and option values as separate shell arguments.

1. Before every dispatch or review, run {{launcher}} roster --json. This is the current project allowlist, CLI/model catalog, default model and effort, login status, capability level, user notes and rules. Choose the CLI, exact model ID and supported effort that fit the task and the user’s rules. Do not prefer one backend automatically. Unknown login or model information means the CLI did not report it; do not invent a value or inspect credential files. If necessary, direct the user to Settings in cc-bro ui for detection or their CLI’s own login.
2. Dispatch with {{launcher}} say research "the task" --worker WORKER --model MODEL --effort LEVEL --bg --json. Omit model or effort to inherit the configured default. Cursor accepts model variants; --effort on an explicit model first resolves a listed variant, then falls back to its [effort=...] parameter. Verify that the model supports it. pi IDs are per provider, such as pi:openai-codex; a pi model must be provider/model-id. Custom workers use custom:name and only the optional arguments their tested template declares. Reuse a name to continue its native session, or choose another name for parallel work. A name stays bound to its worker; model and effort may change between completed turns.
3. Read every receipt, including capability, note, rules and reminders. The allowlist is a hard boundary. Rules are soft reminders for you to evaluate; the CLI does not judge natural-language compliance. If you diverge, explain why to the user. Settings apply on the next dispatch; an active turn keeps its current settings. A queued turn is checked against the allowlist again before starting.
4. Immediately start a Bash tool call with run_in_background: true running {{launcher}} wait research 1 --json, substituting the exact name and turn from the receipt. A receipt is not a successful result. After notification, inspect {{launcher}} show research --json, verify the result, request revisions if needed and use {{launcher}} done research to accept.
5. After interruption use {{launcher}} ls --json and reattach wait to the recorded turn. show --all gives history; stop cancels; ui opens the board and Settings. If no project is registered, tell the user to run cc-bro init at its root and choose an allowlist and default worker. Do not silently broaden a project policy.
6. Choose --worktree on the first say for parallel code changes or an independent diff. It starts at committed HEAD, not the manager’s uncommitted files. Omit it for research or tasks needing the current checkout. The manager makes this choice; cc-bro never adds it automatically. Reuse the name to retain its checkout.
7. Clarify active work with say on the same name. outcome=injected confirms current-turn delivery. outcome=queued means wait for the returned next turn, even if the current turn has finished. agy, cursor-agent and custom templates queue follow-ups. outcome=rejected means inspect the reason; if delivery was uncertain, inspect show --all before retrying. Do not change model or effort in a running turn, guess turn numbers, or create a second writer to duplicate the instruction.
8. Use {{launcher}} review auth-fix --by WORKER --model MODEL --bg --json after the writer finishes when an independent check is useful, especially for risky changes. Choose a different allowed worker ID. The reviewer gets the writer’s final reply, instructions and Git file summary in its checkout. Wait using the review receipt’s own name and turn; leave the checkout unchanged during review. Ask the original writer for fixes and create a new review after the next turn. For a Claude review, use your own native Claude Code subagent; Claude is the manager, not a cc-bro worker.
9. User notes take priority. If you learn something useful about a bro, propose it with {{launcher}} note WORKER "suggested note" --json. This only creates a pending proposal. Tell the user to accept or dismiss it in Settings. Never accept a proposal for the user or overwrite their note through the settings API.
10. Accept the reviewer and writer separately. done prints a worktree cleanup reminder. The manager decides what to preserve, merge or remove; cc-bro never merges or deletes the worktree. A custom CLI has degraded capabilities: reliable ID resume and replies, cc-bro queue/stop/review/worktrees, but no native current-turn steering, detailed steps or cache metrics.
